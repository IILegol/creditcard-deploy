Архитектура сервиса

Выбор подхода: Монолит

В данном учебном проекте выбран монолитный подход, так как:
- Сервис решает одну задачу (скоринг кредитных карт).
- Одна модель, один домен, нет необходимости в независимом деплое компонентов.
- Минимальная операционная сложность: один контейнер, один эндпоинт.

Микросервисы были бы избыточны на этом этапе, но могут стать 
необходимыми при масштабировании.

Концепт брокера сообщений (RabbitMQ)

При росте нагрузки можно внедрить RabbitMQ:
- Асинхронная обработка батчевых предсказаний (клиент кидает задачу в очередь, воркеры обрабатывают параллельно).
- Логирование событий в отдельную очередь для дальнейшей агрегации.
- Разделение на приоритетные и обычные запросы.

Логирование и мониторинг

В production логи агрегируются через ELK-стек:
- Filebeat/Fluentd собирают JSON-логи с контейнера.
- Logstash парсит и фильтрует.
- Elasticsearch хранит.
